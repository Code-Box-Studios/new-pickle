# Supabase Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan
> inline, with one fresh code review at the end.

**Goal:** Switch Pikol's database configuration, auth, and persistent uploads to Supabase.

**Architecture:** Preserve Prisma and Payload over PostgreSQL. Supabase Auth owns
sessions and verified identities; Pikol owns application IDs, live roles, and
booking permissions. Supabase Storage backs the current authorized file routes.

**Tech Stack:** Next.js 16, Prisma 5, Payload 3, @supabase/ssr, @supabase/supabase-js.

**Spec:** docs/superpowers/specs/2026-10-03-supabase-design.md

## Global Constraints

- Work directly on main. Preserve user changes to ignore files and pnpm lockfile.
- No additional questions or hosted credentials invented.
- Verify Supabase users; never derive Pikol roles from user metadata.
- Preserve historical IDs and PostgreSQL overlap protection.
- Production uploads use private Supabase Storage through authorized server routes.

## Review Focus

- A verified email and phone belonging to separate accounts must not merge privileges.
- Revoked roles and inactive users must lose access despite a valid Supabase session.
- Failed OTPs or identity binding must not set a signed-in cookie.
- Cookie refresh and logout must propagate every cookie chunk and disable caching.
- Browser database access must not expose bookings, credentials, or CMS drafts.
