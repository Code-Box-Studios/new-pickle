# Pasalo implementation plan

**Spec:** `docs/superpowers/specs/2026-10-15-pasalo.md`
**Execution:** Continue directly on main, as authorized by the user. Preserve unrelated working-tree changes. Use one final feature commit after verification.

## Task 1: Contract and transaction service

- Write failing integration tests for listing eligibility, competing claims, private conversations, payment declarations, transfer idempotency, and actual Manila cutoff.
- Add three private Prisma models and an additive migration with foreign keys, checks, indexes, RLS, and an active-claim unique index.
- Implement booking-lock transactions, expiry, text message limits, and browser-safe DTOs.
- Run `npm test -- tests/pasalo/service.test.ts`.
- Expected: tests fail before implementation and pass afterward.

Interfaces: produces `PasaloListingView`, `PasaloThreadView`, service actions, and `publicListing`/`myPasalo`/`tradeThread` read functions for Task 3. Serialized dates use ISO strings; prices are integer centavos. No public payment details.

## Task 2: Booking access and invalidation

- Write failing tests for receipt/proof privacy after transfer and stale seller cancellation.
- Integrate listing guards and actor revalidation inside locked local booking mutations.
- Redact original receipts for the transferred buyer while preserving authorized original-payer and venue access.
- Run Pasalo tests plus booking/payment/proof regression tests.
- Expected: all affected suites pass.

Interfaces: consumes Task 1's listing relation and locked invalidation helper; preserves existing booking API signatures.

## Task 3: Routes and responsive interface

- Add authenticated, same-origin mutation routes and private conversation reads with no-store responses.
- Add discovery, offer details, private chat/payment actions, and personal buying/selling pages.
- Integrate listing creation and transferred receipts on booking pages; add navigation links.
- Test authorization, malformed requests, and payment action visibility. Inspect mobile and desktop in a real browser.
- Expected: direct payment is clearly disclosed; guests can browse without accounts; every mutation requires authenticated access.

Interfaces: consumes the Task 1 DTOs and service actions. UI cannot import Prisma or server-only code.

## Task 4: Verify, review, and document

- Integrate the separate player-statistics scope document and update the README.
- Run full tests, lint, typecheck, and production build. Request an independent review of transaction races, sensitive-data exposure, and UI flow.
- Fix important findings with regression tests, commit only owned files, and report deployment status truthfully.
- Expected: verification commands pass; PayMongo payouts and player stats are never described as implemented.

Review focus: booking-lock order, alternate mutation endpoints, server-managed sender identity, wallet information in public payloads, original-payer proof access, actual-time versus wall-clock comparisons, stale actor races, expiry after payment is declared, and responsive private trade controls.
